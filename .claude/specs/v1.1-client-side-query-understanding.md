# v1.1 — Client-supplied query understanding

Status: **Draft.** Nothing here is implemented. Targets release v1.1.0.

## 1. Context

v1.0 deploys to a free-tier VM (AWS micro or Oracle Always Free). Those machines cannot run Ollama
alongside Spring Boot and PostgreSQL, and the Oracle A1 allowance is itself unstable (reported cut to
2 OCPU / 12 GB; unverified). So **v1.0 ships with `knowledge.ai.enabled=false`**: search uses the
deterministic analyzer plus PostgreSQL FTS and metadata filters, and no embeddings are generated.
That is a supported configuration (README, `application.yaml`), not a degraded one.

v1.1 lets the *reader's device* do the interpretation, so a small server needs no model runtime.

## 2. Goal

Let the frontend, on devices that can run a small language model locally, interpret a query into a
`SearchIntent` and send it to the backend, which validates it and runs the normal search flow.

Non-goals:

- No server-side model. The existing `SpringAiQueryUnderstandingModelImpl` path is untouched and
  stays available for when paid hardware exists.
- No client-side embeddings. Query vectors must come from the same model as stored document vectors
  (`nomic-embed-text`, 768 dimensions); that is a separate decision (§9).
- No change to ranking, retrieval, or the `SearchIntent` shape.

## 3. Principles preserved

- **SLM interprets, search retrieves.** The client produces an intent and nothing else. It cannot
  name SQL, repositories, indexes or ranking.
- **Model output is untrusted.** A client-supplied intent is *more* untrusted than server-side model
  output, because the caller is arbitrary. It goes through the same `SearchIntentValidator`.
- **Unavailable intelligence degrades, never breaks.** No client model, invalid intent, or a disabled
  feature all fall back to today's deterministic path.

## 4. Design

### 4.1 API

Additive, backward compatible. `GET /api/search` is unchanged.

New: `POST /api/search`

```json
{
  "q": "articles by Harsh about kubernetes networking",
  "page": 0,
  "size": 0,
  "intent": {
    "intent": "ARTICLE_SEARCH",
    "author": "Harsh",
    "topics": ["kubernetes"],
    "tags": [],
    "queryText": "kubernetes networking",
    "dateRange": null,
    "mode": "HYBRID"
  }
}
```

- `q` is required and is always the reader's original text. It bounds the validator's fallback and
  is what gets logged and cached against.
- `intent` is optional. Absent, the request behaves exactly like `GET`.
- Response is the existing `SearchResponse`. It already reports `usedQueryUnderstanding` and the
  interpretation; add a field `interpretationSource`: `DETERMINISTIC | SERVER_MODEL | CLIENT`, so a
  surprising result can be traced to who interpreted it.

`POST` rather than a JSON query-string parameter: the intent is structured, URL length and logging of
query strings are both concerns, and it leaves `GET` cacheable and simple.

### 4.2 Search flow

`DefaultSearchServiceImpl.understand(...)` gains one branch, ahead of the analyzer decision:

```
client intent present?
  yes -> SearchIntentValidator.validate(clientIntent, q)
           valid   -> Understanding(validated, source=CLIENT)
           invalid -> fall through (deterministic parse), count + log
  no  -> existing path (analyzer -> server model | deterministic)
```

The planner, retrievers and ranker are not modified. `DefaultSearchServiceImpl` already centralises
this decision, so the change stays in one method plus a new overload on `SearchService`.

### 4.3 Validation (reuse, then tighten)

Reuse `DefaultSearchIntentValidatorImpl`. Before implementing, review it against a hostile caller
rather than a confused model: bounds on list sizes and string lengths, enum values, date-range
ordering and span, `queryText` length against `max-query-length`, control characters. Gaps found
become validator tests, not client-specific code. Resolution of `author`, `topics` and `tags` to
identities stays server-side and unchanged.

### 4.4 Feature flag

`knowledge.search.client-intent.enabled`, default `false`. Independent of `knowledge.ai.enabled`
(the server model must stay off on the free VM while client intents are on). When disabled, a
supplied `intent` is ignored and counted, not rejected, so a newer frontend still works against an
older backend configuration.

### 4.5 Abuse and cost

Interpretation cost has moved to the client, so the server's added exposure is validation only,
which is cheap. Search itself still costs a database query per request.

- Search is a public endpoint today. Confirm what rate limiting exists; if none, add per-IP limiting
  at the gateway (APIM) rather than in the application. Open question O1.
- Cache key must include the validated intent, not just `q`, or two readers' different
  interpretations would poison each other's cache entries.

### 4.6 Frontend (separate repository; recorded here for the contract)

- Feature-detect, lazily. Try Chrome's built-in Prompt API first (no model download by us); consider
  a WebGPU runtime (WebLLM / transformers.js) only if measurement justifies a large download.
  Both are from memory and need re-verifying at implementation time.
- Never block search on the model. Send the query without an intent if the model is not ready or
  does not answer within a short budget.
- The prompt and the JSON schema must come from one source of truth. Publish the `SearchIntent`
  JSON schema from the backend's OpenAPI spec and generate the client type from it.

## 5. Observability

Extend the existing `knowledge.search.understanding` counter (`path` tag) with `client`,
`client_invalid`, `client_ignored` (flag off). Keep tag cardinality fixed. Log a rejected intent at
`WARN` with the validation reason and the query length, never the full intent body or any
identifying data. Add `interpretationSource` to the search duration timer tags.

## 6. Security

- Treat the intent as user input. No field is ever interpolated into SQL, a filesystem path, a log
  format string, or a prompt (a later server-side model would also see `queryText`).
- Request size limit on the POST body.
- Unknown JSON properties are rejected, not ignored.

## 7. Testing

- Unit: validator against hostile intents (oversized lists, bad enums, inverted/huge date ranges,
  empty and over-long `queryText`).
- Unit: `understand(...)` branch table — flag off, intent absent, intent valid, intent invalid.
- Integration (Testcontainers; skips without a runtime, like the existing ITs): `POST` with and
  without intent returns the documented response; invalid intent yields the deterministic result
  and `interpretationSource=DETERMINISTIC`.
- Contract: `apim/api-spec.yaml` regenerated and diffed; `GET /api/search` response unchanged.

## 8. Rollout

1. Backend behind the flag, off. Deploy; confirm no behaviour change.
2. Enable on a test environment; frontend experiment against it.
3. Measure the valid-intent rate and the result quality difference versus deterministic parsing.
4. Enable in production only if the measurements justify the extra frontend complexity.

Rollback is the flag; there is no schema change and no migration.

## 9. Open questions

- **O1.** What rate limiting exists in front of `/api/search`?
- **O2.** Can a browser run `nomic-embed-text` compatibly with the stored vectors? Until verified,
  semantic search stays server-side or off.
- **O3.** Is the Prompt API stable and available enough on target browsers to be the first choice?
- **O4.** Should `understand=true|false` (existing GET override) also be accepted on `POST`, or is it
  superseded by `intent`? Leaning: accept it, same meaning, ignored when `intent` is present.
